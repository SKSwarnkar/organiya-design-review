Framing contract

  • Product cards: retain Option O’s 4:5 frame. Commission or generate the asset at 4:5; validate its dimensions before publication. Never stretch a landscape image into it.
  • Gallery stage and thumbnails: use the selected image’s actual width/height ratio from content/media.json. Full images remain visible without letterboxing. A future landscape image gets a landscape frame.
  • Family cards: use the new portrait compositions at their native ratio, with no bars. The American scene is a serving inspiration, not an announcement of US availability.
  • Pouches, nutrition and ingredients: use approved photography or actual label artwork, at native proportions; include accessible text. Never generate label facts, logos, certification seals or nutrient figures.
  • Performance: WebP delivery, explicit dimensions, lazy loading below the fold. Production build generates responsive widths and srcset; keep original masters outside the public build.

Asset workflow for every change

  1. Choose the actual product reference and intended page slot; record provenance and permissions.
  2. Set the aspect ratio before generating. Save the prompt and reference IDs. Keep styling props separate from claims about ingredients.
  3. Inspect snack shapes, people/hands, unwanted text, packaging and colour. Discard inaccurate renders.
  4. Optimise without distorting the image; update the media manifest with dimensions, alt text, caption and status.
  5. Review the exact image on mobile and desktop, then commit the approved file and content reference together.

Rollback

Trigger rollback immediately for a serious content/claim error or data exposure; for a broken critical route, failed TLS or failed contact delivery, use a pre-agreed 15-minute troubleshooting limit. The operator can roll back within the approved launch window without waiting for a second meeting.

  1. New-site code/content issue: pause publishes and restore a known-good production Pages deployment. Restore the matching Git content and asset versions before the next build so the fault does not return. A preview deployment is not a Pages rollback target; the first launch must retain the legacy fallback if no earlier good production deployment exists. Pages rollback procedure.
  2. Domain/TLS or first-release failure: restore the four apex GitHub A records and the www → skswarnkar.github.io CNAME from the snapshot, including prior TTL/proxy state. Remove the conflicting Pages apex CNAME. Pause new redirect rules only where they conflict with the restored host. Keep the legacy GitHub domain binding and HTTPS setting intact.
  3. Verify recovery: check apex/www/HTTPS, representative legacy routes, contact access and email routing on desktop and mobile data. Allow cached DNS to expire; confirm from multiple resolvers. Record the incident, restored release and follow-up fix before attempting another cutover.

Launch record to retain: source branch and commit, content/media manifest, image approval version, build result, Pages deployment ID/URL, zone export and exact DNS diff, TLS status, redirect results, inbox acceptance, founder approval, rollback target and operator.
